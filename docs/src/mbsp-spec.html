Abstract

The MIDI Bulk Storage Protocol (MBSP) lets any MIDI device save and recall its own bulk data, such as patches, banks, performances, drum kits, sequences, tunings and calibration data, on a storage Server reachable over an ordinary MIDI connection. The device itself starts every transfer, so no instrument-specific librarian software is needed: one MBSP Server can serve every MBSP-capable device in a studio. A Server with a user interface may also offer a Record to a device, which fetches it only if the device accepts.

MBSP is carried entirely in Universal Non-Real Time System Exclusive messages and works over MIDI 1.0 DIN, USB MIDI and any transport that carries MIDI 1.0 System Exclusive, including MIDI 2.0 UMP Data 64 messages. It defines discovery of Servers and, optionally, of Clients, acknowledged block-by-block transfer with checksums and recovery of lost messages, server-assigned record identifiers, atomic replacement of stored records, filtered and paged queries, owner-checked deletion, optional offers of Records from a Server to a device, and a classification of bulk data types. The protocol is stateless between transactions and needs only a small amount of memory in the device.

Contents

    1Introduction

    1.1Purpose

    This specification defines the MIDI Bulk Storage Protocol (MBSP): the messages, data structures and procedures that let a MIDI device (the Client) store its bulk data on, and recall it from, a storage device (the Server) over a MIDI connection.

    1.2Background and Motivation

    MIDI instruments have long been able to dump and reload their internal data using manufacturer-specific System Exclusive messages. In practice, saving and restoring that data needs one of three things: "librarian" software running on a computer, which must understand the proprietary format of every instrument it supports; a generic System Exclusive utility, such as MIDI-OX, that records and replays dumps without understanding them; or a dedicated hardware data filer. All three have drawbacks:

    • A typical studio needs several separate librarian applications, each written for particular instruments, and many instruments have no librarian at all.
    • Generic System Exclusive utilities work with any instrument, but leave the user with a growing collection of .syx and Standard MIDI Files scattered across a computer's file system. The files carry no reliable record of which instrument, model or unit they came from, or of what they contain beyond whatever the user typed into the file name. Finding a particular patch means opening files one by one, and organizing, backing up and restoring them is manual and error-prone.
    • Librarians and generic utilities both depend on a computer, which conflicts with the growing number of computer-free ("DAWless") studios and live rigs.
    • Hardware data filers, once common, are now rare, and each instrument must still be operated by hand to send or request a dump.

    MBSP reverses the relationship. The instrument, which already understands its own data, takes responsibility for saving and restoring it, and the storage device becomes a simple, unattended, instrument-agnostic service. The Server never needs to interpret the data it stores, yet every Record carries the metadata that loose dump files lack: the device it came from, its slot number and name, its kind, and the user's tags. A Client can therefore search a Server for exactly what it needs. Any device that implements MBSP can use any MBSP Server, whether it is a computer application, a dedicated hardware box, a feature of a MIDI interface, or a web page.

    1.2.1Why Now?

    Manufacturer-specific bulk dumps are a long-established practice, and the large installed base of MIDI devices will not use MBSP unless their firmware or software is updated. MBSP is therefore aimed mainly at devices still to come. Two current trends make this the right time to define it:

    • Low-cost instruments. A growing number of inexpensive instruments are built on resource-constrained hardware, with little room to store patches and rarely any librarian software.
    • Replacement and enhanced firmware. It has become far easier for individuals and small teams, increasingly with the help of AI coding tools, to write new or improved firmware. This is happening especially for low-cost instruments, and for vintage units whose original storage is severely limited.

    Both kinds of device need somewhere to keep their data. Defining a standard mechanism now, carried in the System Exclusive messages that every MIDI device already supports, lets new instruments and updated older ones manage off-device storage from the start, instead of each inventing its own scheme.

    1.3Scope

    This specification defines:

    • The System Exclusive message envelope and every MBSP message (Section 4 and Section 6).
    • The common data structures carried in those messages (Section 5).
    • The procedures for discovery, Store, Retrieve, Query, Delete and Offer, including error handling and timeouts (Section 7).
    • Conformance requirements for Servers and Clients (Sections 8 and 9).

    The following are outside the scope of this version:

    • The format or meaning of the stored data. Payloads are opaque to the Server.
    • How a Client presents MBSP functions to its user.
    • How a Server stores records internally, backs them up, or exchanges them with other Servers.
    • Authentication, authorization and encryption (see Section 10).

    1.4Design Goals

    • Device-initiated. The Client decides what to save and when, and restores its own data without a computer. A Server may offer a Record to a Client, but only the Client decides whether to load it.
    • Works on MIDI 1.0. Every message is a valid MIDI 1.0 System Exclusive message, usable over 31.25 kbaud DIN connections, mergers and splitters.
    • Small footprint. A Client needs to hold only one data block and a few counters at a time. No sessions or connection state are kept between transactions.
    • Data-agnostic Server. The Server stores opaque payloads with a small amount of descriptive metadata, so one Server serves every device.
    • Coexistence. MBSP traffic can share a MIDI network with other devices, which ignore it, and with several Clients and Servers at once.

    3Protocol Overview

    3.1Roles

    A Client initiates every Transaction that transfers or changes data. A Server sends Replies, and only three kinds of message unprompted, all optional: OnlineServer announcements (Section 6.2), DiscoverClients (Section 6.4) and Offers (Section 7.7). An Offer only proposes a Record: the Client decides whether to accept it, and fetches it with a Retrieve of its own. A device may act as both a Client and a Server, but the two roles are independent.

    3.2Network Model

    MBSP needs a two-way MIDI connection between each Client and the Server it uses, because every operation, including discovery, is a Request followed by Replies. Over MIDI 1.0 DIN this means a cable or route in each direction. A Client that can only send to a Server, or only receive from it, cannot use MBSP.

    MBSP assumes a MIDI network in which every message may reach every device, as happens with MIDI mergers, splitters, Thru chains, multi-port interfaces and software routing. All MBSP messages are therefore sent to the All Call device ID (7Fh), and addressing is done inside the message:

    • Every message carries the sender's Source MUID and the recipient's Destination MUID (Section 4.5). A device ignores any message whose Destination MUID is neither its own nor the broadcast MUID.
    • Clients and Servers each draw a random MUID at power-up. A Client finds Servers, and learns their MUIDs, through discovery (Section 7.1). A Server may likewise discover Clients, to show its user which devices are present and to address Offers to one of them. The Server Name is a display name that Servers announce in OnlineServer.
    • Requests and Replies carry a Transaction ID chosen by the Client, so a Client can have several Transactions open at once. Only DiscoverClients and Offer carry a Transaction ID chosen by the Server.

    MBSP does not route or forward messages. Discovery reaches exactly the devices that the MIDI routing connects to the Client in both directions. A device with several MIDI ports may use MBSP on any of them, and should send its Requests to a Server on the port where it discovered that Server. Section 11.3 covers MIDI 2.0 UMP Groups.

    Devices that do not implement MBSP ignore MBSP messages, because MIDI 1.0 requires receivers to ignore Universal System Exclusive messages whose Sub-IDs they do not recognize.

    3.3Transactions and Statelessness

    MBSP has no sessions, connections or logins. Every Transaction is complete in itself. A Store or Retrieve Transaction spans several messages, so the receiving side keeps temporary reassembly state, keyed on Client MUID and Transaction ID, until the Transaction completes or times out. No state carries over from one Transaction to the next.

    Store and Retrieve transfers are flow-controlled: the receiver acknowledges each Block and asks for the next one, so a sender never sends faster than the receiver can process (Section 7.4).

    4.2Protocol Version

    This specification defines Protocol Version 1. A receiver must ignore any message whose Protocol Version it does not implement, because the layout after the Version byte may differ.

    Discovery is the exception, so that a Client can always find out which versions a Server supports:

    • A Server shall answer DiscoverServers whatever its Protocol Version. DiscoverServers has an empty payload in every version.
    • A Server shall always send OnlineServer with Protocol Version 1, so that every Client can read it. Its Supported Versions field lists every Protocol Version the Server implements, and the Client then uses one of them for its Requests.
    • Later versions may append fields to OnlineServer but shall not change the fields defined here. A Client shall ignore any bytes after the OnlineServer fields it knows.

    4.3Sub-ID #2

    Sub-ID #2 00h identifies the base protocol defined here. Other values are reserved for future extensions of MBSP, which may define their own message sets. A receiver must ignore messages with a Sub-ID #2 it does not implement.

    4.4Access Key

    The Access Key is an optional string of 0-16 printable ASCII characters that a Server may require before it accepts Store, Retrieve, Query or Delete Requests. Its meaning is defined by the Server's configuration, not by this specification. A Server that requires a key and receives a Request without the matching key shall reply with Status 2 (Refused). The one exception is a Retrieve that follows an Offer the Client accepted (Section 7.7). Servers should answer DiscoverServers whatever the key, so that Clients can always find them.

    Keys are compared byte for byte, so letter case and spaces are significant. A Server with no configured key accepts every Request, whatever key it carries. The key is checked on the Request that opens a Transaction (Store_Header, Retrieve_Request, Query_Request or Delete_Request), and a change of the Server's key does not affect Transactions already open.

    Servers should send Replies with an Access Key Length of 0. Clients must not depend on the Access Key of a Reply. The Access Key is sent in clear text and provides no protection against a party that can observe MIDI traffic (Section 10).

    The value 0FFFFFFFh (sent as 7F 7F 7F 7F) is the broadcast MUID. Only DiscoverServers, OnlineServer, DiscoverClients, OnlineClient and Offer are sent to it, and it is never a Source MUID. The Server Name plays no part in addressing.

    4.6Transaction ID

    The Transaction ID is a 14-bit number chosen by the Client. A Client shall give each new Transaction a Transaction ID that is not in use by any of its open Transactions, and should do this by incrementing a counter that wraps from 3FFFh to 0. Transaction IDs only need to be unique for one Client MUID. Every message belonging to a Transaction, including Data Blocks and all Replies, carries the same Transaction ID.

    The exceptions are the two messages a Server initiates, DiscoverClients and Offer. A Server shall choose their Transaction IDs from a counter of its own in the same way, skipping 0, and the Client messages that answer them (OnlineClient and Offer_Reply) carry the same value. These Transaction IDs only need to be unique for one Server MUID. They are separate from the Client's own Transaction IDs: DiscoverClients and Offer are never Replies, even when their Transaction ID equals one the Client is using. Announcements, by Servers and by Clients, use Transaction ID 0.

    4.7Message Checksum

    The Message Checksum covers every byte after F0h up to, but not including, the checksum byte itself. It uses the algorithm widely used in Roland System Exclusive messages:

    checksum = (128 - (sum of covered bytes modulo 128)) modulo 128

    Equivalently, the covered bytes plus the checksum sum to a multiple of 128. For example, the DiscoverServers message in Appendix A covers the bytes 7E 7F 6A 00 01 00 56 68 48 00 7F 7F 7F 7F 01 00 00, which sum to 1,131 (46Bh). 1,131 modulo 128 is 107, so the checksum is 128 - 107 = 21 (15h).

    The Message Checksum protects each message on its way across one MIDI link and detects any error confined to a single one of the bytes it covers. Payloads are also protected end to end by the stronger CRC-32 Full Payload Checksum (Section 5.11).

    4.8Reception Rules

    A receiver shall silently ignore a message (send nothing in reply) if any of the following is true:

    • Bytes 1-4 are not 7E 7F followed by the MBSP Sub-ID #1 and a supported Sub-ID #2.
    • Any byte between F0h and F7h is greater than 7Fh.
    • The message is too short to hold the envelope, or the Access Key Length is greater than 16.
    • The Message Checksum is wrong.
    • The Protocol Version is not implemented, except for DiscoverServers (Section 4.2).
    • The Destination MUID is neither the receiver's own MUID nor the broadcast MUID, or the message is sent to the broadcast MUID but is not DiscoverServers, OnlineServer, DiscoverClients, OnlineClient or Offer.
    • The Message Type is not defined in the Protocol Version the receiver implements. The receiver cannot know the message's layout or what reply, if any, it expects.

    A message whose Source MUID is the receiver's own MUID is either an echo or a sign of a MUID collision, and is handled as described in Section 5.5.

    Errors found after the envelope has been accepted are handled as described for each message in Section 6 and in Section 8.

    5Common Data Structures

    5.1Server Name

    A string(4-16), such as "StudioVault", that users know a Server by. It is carried only in OnlineServer. Servers are addressed by MUID, not by name (Section 4.5), so a Client that knows a Server by name looks up its current MUID through discovery (Section 7.1).

    • A Server's name should be configurable by its user, and should be unique on the network. Names are compared byte for byte (case-sensitive).
    • A Server should give itself a default name that is unlikely to match another unit's, for example by adding part of its serial number ("Vault-3F2A"), rather than giving every unit the same name.
    • Two Servers with the same name still work correctly, because each has its own MUID, but users cannot tell them apart. A Client that discovers several Servers with the same name shall not choose one of them automatically (Section 7.1).

    5.2Device Identity

    A 7-byte structure that identifies the make and model of a device. It uses the values the device already returns in its Universal Device Inquiry reply (F0 7E <device> 06 02 ...), so most devices can supply it without new constants.

    Table 4. Device Identity
    FieldBytesDescription
    Manufacturer ID3A 1-byte ID is sent as <ID> 00 00. A 3-byte ID (00 xx xx) is sent as-is.
    Device Family Code2As in the Device Inquiry reply, least significant byte first.
    Device Family Member (Model) Code2As in the Device Inquiry reply, least significant byte first.

    Device Identity is the machine-readable key used for matching in Query, Delete and Offer. Servers do not need, and should not rely on, tables that translate Device Identities into product names. The Client Device Name serves that purpose.

    5.3Client Device Name

    An optional string(0-32) chosen by the Client for display, such as "Juno-106" or "Studio Prophet". Length 0 means not provided. Servers should display it as received and shall not use it for matching.

    5.4Client Device SysEx ID

    One byte holding the device's own System Exclusive Device ID (00h-7Eh), or 7Fh for "not provided". It tells apart several units of the same model on one network, for example two identical synthesizers set to Device IDs 00h and 01h. Device Identity together with Client Device SysEx ID identifies a single unit and is used as the Record's Owner.

    NoteIf a user changes a device's SysEx Device ID, Records stored before the change no longer match queries filtered on the new ID. They remain reachable by querying with the SysEx ID filter set to 7Fh (any).
    NoteSeveral units of the same model that all send 7Fh share one Owner identity, so the Owner-only Delete policy cannot tell them apart, and each can replace or delete the others' Records. Such devices should let the user set a SysEx Device ID. A persistent identifier for each unit is an open issue (Section 12).

    5.5MUID

    A 28-bit value that identifies a Client or a Server on the network until it next powers up, modelled on the MUID of MIDI Capability Inquiry (MIDI-CI).

    • Every Client and every Server shall generate its own MUID as a random number, at power-up or when MBSP starts. No central authority assigns MUIDs.
    • The random number shall not be predictable from one power-up to the next. A device shall not use a fixed seed, or one that is the same at every start, such as a timer read straight after reset. It should mix something unique to the unit, such as a serial number or chip ID, with a source that varies, such as analog noise or the timing of user input. Otherwise identical units switched on together would draw the same MUID every time.
    • Values 0FFFFF00h-0FFFFFFEh are reserved and 0FFFFFFFh is the broadcast MUID. A device that draws one of these values shall draw again.
    • A device that contains several independent Clients or Servers shall give each its own MUID.
    • A device should generate a new MUID at every power-up. The MUID is therefore not a persistent identity: it is never stored with a Record, and a Record's Owner is identified by Device Identity and SysEx ID instead (Section 5.4).
    NoteA Server may instead keep its MUID across power cycles, so that its Clients do not need to rediscover it after it restarts. It may do so only if the MUID was generated on the unit itself. A MUID stored in a firmware image or copied from another unit would give every such unit the same MUID. A Server that keeps its MUID shall still replace it when it detects a collision, and Clients shall not rely on a Server keeping its MUID.

    Collisions. Two devices with the same MUID would each receive the other's messages. A device detects this when it receives a message whose Source MUID is its own but which it did not send:

    • The device shall first rule out an echo of its own message, which a MIDI loop or Thru connection can send back. A message identical to one the device sent within the last few seconds is an echo, and is ignored.
    • Otherwise the device shall abandon its open Transactions, generate a new MUID and use it from then on. A Server shall then announce its new MUID by broadcasting OnlineServer with Transaction ID 0, so that its Clients can follow it. Their Transactions that were open on the Server fail, and they may retry them. A Client that implements client discovery announces its new MUID with OnlineClient (C-16).

    With truly random MUIDs, collisions are very rare: for a network of ten devices, about 1 in 6 million at each power-up. The rules above mainly protect against weak random number generation.

    5.6Record ID

    A u21 assigned by the Server when a Store succeeds, unique among that Server's Records. Record ID 0 is reserved and means "no Record" or "not applicable". A Server shall give each new Record a Record ID higher than any it has assigned before, so it never reuses the Record ID of a deleted Record: a Client holding an old Record ID receives Not Found rather than different data, and Records stored during a paged Query appear only after the existing ones (Section 7.5). This continues across power cycles, and a Server that restores a backup continues after the highest Record ID it has assigned or restored. When no Record IDs remain, the Server replies to Store with Status 6 (Storage Full). A Store that replaces a Record keeps that Record's ID (Section 7.2).

    5.7Payload Number and Payload Name

    The Payload Number is required. It is a string(1-8) giving the item's location or number on the device, such as "B22", "099" or "I-05". Every device can name the slot an item came from, and the number is what a Client uses to put retrieved data back in the right place. For data that has no slot, such as global settings or calibration, the Client uses a fixed descriptive string such as "GLOBAL" or "CAL". A Store whose Payload Number is empty shall be answered with Status Invalid Request (8).

    The Payload Name is optional. It is a string(0-32) giving the item's name, such as "Mini Lead". Length 0 means not provided, for example for a device that does not name its patches or for data such as calibration that has no name. Servers shall accept a Payload Name of length 0 and should display such Records by their Payload Number. A Record without a name never matches a non-empty Payload Name Filter.

    Both are chosen by the Client and are stored and returned unchanged.

    5.8Tags

    A tag list is a u7 count (0-8) followed by that many string(1-16) tags, such as "Pad", "Bass" or "Live Set 3". Tags help users and Clients find Records. Servers store tags as received and compare them without regard to ASCII letter case.

    5.9Client Payload Type

    One byte that classifies the Payload. It is made of two parts:

    • Bits 0-5: Category (00h-3Eh), from Table 5. Category 3Fh is reserved and never used.
    • Bit 6 (40h): Collection bit. 0 = a single item, 1 = a collection (bank) of items of that Category. For example, 01h is a single Patch and 41h is a Bank of Patches.

    5.11Full Payload Checksum

    A u32 carried in Store_Header and Retrieve_Header. It is the CRC-32 of the complete Payload, computed over the Payload bytes in Block order, using the CRC-32 of IEEE 802.3 and zlib:

    Table 7. Full Payload Checksum (CRC-32) parameters
    ParameterValue
    Polynomial04C11DB7h (EDB88320h in reflected form)
    Initial valueFFFFFFFFh
    Input and output reflectedYes
    Final XORFFFFFFFFh
    Check valueCBF43926h for the ASCII string "123456789", sent as 26 72 50 5F 0C

    The Client computes the CRC-32 before a Store. The Server checks it after reassembly, stores it with the Record, and returns it unchanged in Retrieve_Header, and the Client checks it again after a Retrieve. It therefore protects the Payload end to end: across reassembly, the Server's storage, any backup and restore, and the return trip. Unlike an additive checksum, it also detects Blocks reassembled in the wrong order. A table-free implementation needs only a few lines of code and keeps up easily with MIDI data rates on small microcontrollers.

    7Procedures

    7.1Discovery

    A Client finds Servers by sending DiscoverServers to the broadcast MUID and collecting OnlineServer replies for a short period. A wait of 1 second is recommended. Each reply gives a Server's MUID (its Source MUID) and its name. A Client may also learn of Servers from announcements, which it may use at any time (C-2).

    Servers draw a new MUID at power-up (Section 5.5), so a Client shall discover the Server it uses before its first Request after the Client powers up, even when it has been configured with a Server Name. It should discover again when a Server it was using stops answering, which usually means the Server has restarted with a new MUID. It should also follow a Server that announces a new MUID with OnlineServer under the same name.

    If several Servers answer with the same name, a Client shall not choose one of them automatically. It should tell its user, who can rename one of them, and may let the user choose between them by other details, such as their policies.

    OnlineServer tells the Client how to use each Server: which Protocol Version to speak, whether it accepts Stores, Deletes and firmware, whether it needs an Access Key, the largest Store Block it accepts, and roughly how much it can still store. For example, a Client can offer firmware backup only to Servers that accept firmware, and choose a Block size no larger than the Server's Max Store Block Size.

    Client discovery (optional). A Server that wants to know which Clients are present, for example to let its user send a Record to one device, sends DiscoverClients to the broadcast MUID and collects OnlineClient replies for the Server client-discovery wait (Table 9). Clients that implement client discovery also announce themselves with OnlineClient to the broadcast MUID at power-up and whenever their MUID, SysEx Device ID or Device Name changes, so a Server learns of them without asking. A Server keeps what it learns in a device list, keyed by Client MUID:

    • The device list is advisory. It is used only to show the user which devices are present and to address Offers. A Server shall not use it in place of the Device Identity and SysEx ID carried in Store_Header and Delete_Request: ownership is always taken from the Request itself.
    • An OnlineClient replaces the entry for its Source MUID. When a Client announces a new MUID, the Server cannot know the old one. It may drop an entry with the same Device Identity and SysEx ID under another MUID, when the SysEx ID is not 7Fh. Identical units without a SysEx ID cannot be told apart this way (Open Issue 2).
    • A rediscovery rebuilds the list: entries whose Clients do not answer a new DiscoverClients should be removed. A Server that has just powered up has an empty list and should send DiscoverClients before it relies on the list.
    • The Client Capability Flags tell a Server whether a Client accepts Offers, so that it can avoid sending Offers that will go unanswered.

    Client discovery adds no state that any Request depends on. A Server that loses its device list, or never builds one, still answers every Request correctly.

    7.2Store

    1. The Client sends Store_Header and waits. The Server replies with Store_Block_Ack (Next Block Index 0), or with a Status if it cannot accept the Store. A Server that knows it cannot hold Payload Size more bytes should reply Storage Full (6) at once, before any Block is sent.
    2. The Client sends each Block only when the Server asks for it, in Block Index order. The Server acknowledges every Block except the last (Section 7.4).
    3. The Server reassembles the Blocks. If any check below fails, it discards the Transaction and sends Status with the matching code. It answers any further Blocks of that Transaction by repeating that Status (see Lost final Status below):
      • a Block arrives out of order or after a missing Block: Block Sequence Error (4). A repeat of the Block the Server accepted last is not an error (Section 7.4);
      • no Block arrives within the Store Transaction Timeout (Table 9): Transaction Timeout (5);
      • a field is malformed, Payload Size cannot fit in NumBlocks Blocks of the Server's Max Store Block Size, a Block is larger than that size, or the Blocks add up to more or less than Payload Size: Invalid Request (8).
    4. When the last Block has arrived, the Server checks the Full Payload Checksum (failure: Payload Checksum Error, 3), writes the Record, and replies with Status OK carrying the new Record ID. The Record shall not become visible to other Requests before this point.

    A Client shall choose a Block size that carries the Payload in no more than 16,383 Blocks. Blocks of 128 bytes are enough for a Payload of any size, and every Server accepts Blocks of at least 256 bytes (S-11).

    An empty Payload is stored as one Block of size 0 (NumBlocks = 1). Its Full Payload Checksum is the CRC-32 of no bytes, 00000000h. An empty Payload is retrieved the same way (Section 7.3).

    The Server may reply with an error Status at any point before the last Block, for example Refused or Busy instead of the first Store_Block_Ack. A Client shall stop sending Blocks as soon as it receives a Status for the Transaction. If a Server receives a second Store_Header with the Client MUID and Transaction ID of a Store in progress, it should discard the earlier Transaction and start again.

    Replacing a Record. A Store_Header with a non-zero Replace Record ID asks the Server to replace that Record instead of creating a new one:

    • When the Store_Header arrives, the Server shall reply Not Found (1) if the Record does not exist, and Refused (2) if its policies forbid deleting that Record: a read-only Server, Delete disabled, or Owner-only Delete when the Store does not come from the Record's Owner (Section 8.4). Otherwise the transfer proceeds exactly as for a new Record.
    • The replacement shall be atomic. The Record keeps its old Payload and metadata until the last Block has arrived and the Full Payload Checksum has been verified. Only then does the Server replace the Payload and all of the Record's metadata with those of the Store. A Store that fails for any reason leaves the Record unchanged.
    • The Record keeps its Record ID, and the final Status OK carries it. Record IDs held by the Client and by other Clients remain valid and now refer to the new version.
    • A Retrieve of the Record that began before the replacement shall return the old Payload and metadata in full, and a Retrieve that begins afterwards returns the new ones. A Client never receives a mixture of the two.
    • If the Record is deleted while the replacement is being transferred, the Server replies Not Found (1) at the end of the transfer.
    • Replacements of the same Record commit one at a time, in the order their transfers complete. Each successful one is answered with Status OK, and the Record holds the Payload and metadata of the one that completed last.

    Replacing a Record is idempotent: repeating the same Store gives the same result, so it combines safely with the recovery of a lost final Status described next.

    Lost final Status. If the final Status of a Store is lost, the Client hears nothing after its last Block, so it resends that Block (Section 7.4). The Store has already ended on the Server, so to answer such resends the Server shall remember the final Status of every Store Transaction, successful or not, keyed by Client MUID and Transaction ID, for the Completed Store Memory time (Table 9). A Store_Data_Block for a remembered Transaction is answered by sending the same Status again, and changes nothing: in particular, it never creates a second Record. A Server may limit how many finished Stores it remembers, but should remember at least as many as it allows at once, forgetting the oldest first. A new Store_Header with the same Client MUID and Transaction ID replaces the remembered Transaction.

    A Block for a Store that is neither open nor remembered is answered with Unknown Transaction (9). A Client that receives this after resending its last Block cannot tell whether the Store succeeded, for example because the Server restarted. It may Query the Server to find out, or store the Payload again.

    7.3Retrieve

    The Server chooses a Block size no larger than the Client's Max Block Size (when given) and no larger than its own limit, and sends Retrieve_Header. The Client answers with Retrieve_Block_Ack (Next Block Index 0) when it is ready, and the Server then sends each Block only when the Client asks for it. The Client's ack after the last Block (Next Block Index = NumBlocks) tells the Server that the transfer is complete. An empty Payload is sent as one Block of size 0. If the Payload cannot be sent in 16,383 Blocks of the Client's Max Block Size, the Server replies Invalid Request (8).

    Retrieve_Header gives the Payload Size before any Block is sent, so a Client can check that the Payload fits in its memory. A Client that cannot accept it does not acknowledge the header. The Server's retries then end the Transaction.

    The Client reassembles the Blocks and checks that they add up to the Payload Size and match the Full Payload Checksum. If either check fails, or the transfer fails after the retries of Section 7.4, the Client discards the data and may send a new Retrieve_Request with a new Transaction ID. If the Server gives up after its retries, it sends Status Transaction Timeout (5) with Request Message Type 20.

    7.4Flow Control and Lost Messages

    Store and Retrieve use the same lock-step scheme, with one message in flight at a time. In a Store the Client sends Blocks and the Server acknowledges them with Store_Block_Ack. In a Retrieve the roles are reversed: the Server sends Blocks and the Client acknowledges them with Retrieve_Block_Ack. Each ack carries the index of the Block the receiver wants next, so it both confirms what has arrived and grants permission to send one more Block. A receiver that needs time, for example to write a Block to flash memory, simply sends its ack later.

    Version 1 deliberately keeps one Block in flight, so that a receiver never needs to buffer more than one Block. The cost is one round trip per Block, which is small on DIN and USB (Section 11.1). A windowed scheme, in which the receiver grants several Blocks at once, would suit high-latency links such as network MIDI, and may be added in a future version. A Client would learn of it from the Supported Versions in OnlineServer.

    The sender of the Blocks (the Client in a Store, the Server in a Retrieve):

    • shall send the header first, and then a Block only when an ack asks for exactly that Block;
    • shall ignore any ack other than the one for the message it sent last. Late or duplicated acks are therefore harmless;
    • should resend its last message (the header or the last Block) if no ack arrives within the Ack Timeout, and should give up after Max Retries resends. A Client gives up by abandoning the Store; a Server gives up by sending Status Transaction Timeout (5).

    The receiver of the Blocks:

    • shall acknowledge the header and every Block it accepts, as described in Sections 6.8 and 6.12;
    • shall, on receiving again the header or the Block it accepted last (because its ack was lost), discard the repeat and send the same ack again;
    • shall treat any other out-of-order Block as an error: a Server replies Block Sequence Error (4), and a Client abandons the Retrieve;
    • in a Store, shall answer a resent Block that arrives after the Transaction has ended by repeating the final Status (Section 7.2). The last Block is answered by the final Status instead of an ack, so this is how a lost final Status is recovered.

    Queries use paging instead of acks. Query_Result messages are not acknowledged. Instead, the Client's Max Results sets the most Query_Results that can arrive in one burst, and the Client asks for the next page only when it is ready. A Client that can handle only one result at a time uses Max Results = 1, which gives the same one-message-at-a-time pacing as the Block acks. This keeps Queries stateless on the Server: it answers each Query_Request and keeps nothing afterwards, so it needs no timers or resends for Queries. A lost Query_Result is recovered by requesting the same page again (Section 7.5).

    The Server's pause between Query_Results (S-8) is a courtesy that eases bursts on slow links. Clients shall not rely on it, because results may arrive back to back, particularly over USB.

    7.5Query and Paging

    The Server orders matching Records by ascending Record ID, so that pages stay consistent between Requests, and returns the matches from Start Index up to Max Results. The Client knows the page is complete when it has received the Result with

    Result Index = min(Start Index + Max Results, Total Matches) - 1

    To read the next page, the Client sends a new Query_Request with Start Index advanced by the number of results received. If a Result Index is missing when the Client's reply wait ends, a Query_Result was lost: the Client may send the same Query_Request again (with a new Transaction ID) and keep the results it is missing. Because Records are listed in ascending Record ID order and new Records always receive higher Record IDs (Section 5.6), Records stored during paging appear only after the existing ones, and a replaced Record keeps its position. Only a Record deleted from an earlier page shifts the pages that follow, which can make a Client skip one Record. A Server shall reply with Status Not Found (1) when no Record falls in the requested page, and shall not send a Query_Result whose Result Index would exceed 16,383.

    7.6Delete

    The Client sends Delete_Request with the Record ID and its own Device Identity and SysEx ID. The Server replies with Status OK, Not Found, or Refused. A Server may refuse every Delete (for example an archival or read-only Server), and may refuse a Delete that does not come from the Record's Owner (Section 8.4).

    7.7Offer

    Offers let the user of a Server send a Record to a device: for example, to load a patch into an instrument from a librarian-style screen on the Server, without operating the instrument's own controls. Offers are optional for Servers and for Clients. A Client that does not implement them ignores MBSP_Offer like any Message Type it does not implement (Section 4.8), so the Server receives no reply.

    1. The Server sends Offer to the broadcast MUID, or to the MUID of one Client, for example one from its device list (Section 7.1), naming the Record and the target device.
    2. A Client that implements Offers ignores, without replying, an Offer whose Target Device Identity differs from its own Device Identity in any of the 7 bytes, or whose Target Device SysEx ID is neither 7Fh nor its own SysEx Device ID. It may also ignore Offers from Servers it does not use.
    3. Each Client the Offer is for replies with Offer_Reply within the Client Offer reply time (Table 9): Accepted, Declined, Busy or Unsupported, or Pending while it asks its user. After Pending, it sends a second Offer_Reply, Accepted or Declined, when the user decides, or Declined if the user has not decided within the Offer Lifetime.
    4. After Accepted, the Client sends an ordinary Retrieve_Request for the offered Record ID to the Server's MUID, with a Transaction ID of its own, and the transfer proceeds as in Section 7.3. The Client checks the Payload as it checks any Retrieve (C-5), and also that the Retrieve_Header's Payload Type, Payload Number, Payload Name and Payload Size match the Offer. If they do not, the Record has changed since it was offered, and the Client discards it.

    The Retrieve is a normal Request, so the Server keeps no Transaction state for the Offer itself. It remembers its Offers only to show their outcome to its user and to apply the Access Key rule below. A Server shall not resend an Offer that received no reply. Silence means that no device the Offer is for is listening, or that none implements Offers. The Server should tell its user so, and the user can try again.

    Access Key. A Server that requires an Access Key shall accept, without the key, a Retrieve_Request for an offered Record from a Client that accepted that Offer, until the Offer Lifetime ends. The Server's own user chose to send the Record, and the Client may never have been given the key. Every other Request from that Client still needs the key.

    Several units. An Offer to SysEx ID 7Fh, or for a model whose units send no SysEx Device ID, reaches every unit of that model, and each may accept it. Each Offer_Reply carries the unit's SysEx Device ID and Device Name, so that the Server can show which units answered. To reach exactly one unit, a Server sends the Offer to that unit's MUID, which client discovery provides (Section 7.1). A Server should not send an Offer to a Client whose OnlineClient says that it does not accept Offers. Open Issue 2 also concerns telling identical units apart.

    Loading offered data. An Offer can arrive while the device is in use. A Client shall not replace data stored in its memory with an offered Payload without its user's confirmation on the device, unless its user has chosen to accept Offers automatically. It may load an offered Payload into a temporary edit buffer without confirmation when that destroys nothing the user has saved. Where the data goes is the Client's decision.

    • S-4A Server shall reply with Status Invalid Request (8) to a Request addressed to it whose payload is malformed: a field out of range, non-printable characters, missing bytes or extra bytes after the last field.
    • S-5A Server shall silently ignore a message whose Message Type it does not implement (Section 4.8).

    8.2Replies

    • S-6Every Reply shall be sent from the Server's MUID to the Client MUID of the Request it answers, with the same Transaction ID.
    • S-7A Server shall send no more than one final Status for each Store Transaction, apart from repeating it unchanged in answer to a resent Block (Section 7.2). For each Retrieve_Request it accepts, it shall answer with either a Status or a Retrieve_Header (which it may resend under Section 7.4), and shall send at most one final Status.
    • S-8A Server should pause between consecutive Query_Result messages, which are not acknowledged. The pause should be configurable; 20 ms is a reasonable default.

    8.3Records and Transfers

    • S-9A Server shall store the Payload and all metadata exactly as received and return them unchanged.
    • S-10A Server shall accept Payload Types with reserved and manufacturer-defined Categories and store them as opaque data.
    • S-11A Server shall announce a Max Store Block Size of at least 256 bytes and accept Store Blocks of any size up to it, and shall accept Payloads of up to 2,097,151 bytes unless it replies Storage Full.
    • S-12A Server should keep Records across power cycles and should offer its user a way to back up and restore all Records. A Server that keeps Records across power cycles should commit each Store and each replacement so that a power failure leaves either the old Record or the new one, never a mixture.
    • S-13A Server shall follow the flow control of Section 7.4: acknowledge every Store_Header and Store Block it accepts, and send each Retrieve Block only when the Client asks for it.
    • S-14A Server shall remember the final Status of each Store Transaction for the Completed Store Memory time and send it again, unchanged, in answer to a Store_Data_Block of that Transaction. It shall reply with Status Unknown Transaction (9) to a Store_Data_Block addressed to it that belongs to no open or remembered Store Transaction.
    • S-15A Server shall answer DiscoverServers whatever its Protocol Version, with an OnlineServer sent with Protocol Version 1 that lists every Protocol Version it implements and gives Policy Flags and limits matching its current configuration (Sections 4.2 and 6.2).
    • S-16A Server shall generate its MUID as described in Section 5.5, and on detecting a MUID collision shall draw a new MUID and announce it by broadcasting OnlineServer.
    • S-17A Server should give itself a default Server Name that is unlikely to match another unit's (Section 5.1).
    • S-18A Server shall replace a Record only when a Store_Header names it in Replace Record ID, shall apply the Delete policies to the replacement, and shall make the replacement atomic, keeping the Record ID (Section 7.2).
    • S-19A Server shall give each new Record a Record ID higher than any it has assigned before (Section 5.6).
    • S-20A Server shall reply Invalid Request (8) to a Store whose Blocks do not add up to its Payload Size, and to a Retrieve whose Payload cannot be sent in 16,383 Blocks of the requested Max Block Size (Sections 7.2 and 7.3).
    • S-21A Server that sends Offers shall offer only Records it holds, shall choose their Transaction IDs as described in Section 4.6, shall not resend an Offer that received no reply, and shall accept a Retrieve of an offered Record without the Access Key from a Client that accepted the Offer, until the Offer Lifetime ends (Section 7.7).
    • S-22A Server shall send nothing in reply to an Offer_Reply, and shall ignore one whose Transaction ID and Record ID do not match an Offer it sent within the Offer Lifetime, or that answers an Offer sent to another Client's MUID.
    • S-23A Server that implements client discovery shall choose the Transaction IDs of DiscoverClients as described in Section 4.6, shall send nothing in reply to OnlineClient, shall ignore any bytes after the OnlineClient fields it knows and any reserved Client Capability Flags, and shall not use its device list in place of the Device Identity and SysEx ID carried in a Request (Section 7.1).

    8.4Policies

    A Server may offer the following policies, each of which results in Status Refused (2). It shall report the policies in force in the Policy Flags of OnlineServer (Table 8).

    • Read-only: refuse every Store, including replacements, and every Delete.
    • No Delete: refuse Delete, and refuse any Store that replaces a Record, since replacing removes the Record's previous contents.
    • Owner-only Delete: refuse a Delete, or a Store that replaces a Record, whose Device Identity (all 7 bytes) and Client Device SysEx ID do not both match the Record's Owner. This is recommended as the default.
    • Access Key: refuse Requests without the configured Access Key (Section 4.4), except a Retrieve that follows an accepted Offer (Section 7.7).
    • No Firmware: refuse Stores of Category 0Eh (Firmware / OS). This is recommended as the default, because a corrupt or mismatched firmware image sent back to a device may make it unusable.

    These policies apply to MBSP Requests. A Server's own user interface may manage any Record.

    A Server may limit how many Transactions it handles at once and reply Busy (7) beyond that limit.

    9Client Requirements

    • C-1A Client shall generate its MUID as described in Section 5.5, use it as the Source MUID of every message it sends, and draw a new MUID when it detects a collision.
    • C-2A Client shall ignore messages whose Destination MUID is neither its own nor the broadcast MUID, and Replies whose Transaction ID belongs to no open Transaction. Announcements, DiscoverClients and Offers are the exceptions: a Client may use an OnlineServer sent to the broadcast MUID at any time (Sections 5.5 and 6.2), answers DiscoverClients as described in Section 6.4, and handles an Offer as described in Section 7.7. A Client shall ignore messages that only Clients send (Message Types 0, 4, 10, 11, 20, 23, 30, 40 and 51), which reach it from other Clients, unless it also acts as a Server.
    • C-3A Client shall ignore Replies whose Source MUID is not the MUID of the Server it addressed.
    • C-4A Client should tolerate duplicate Replies, which can occur on networks with mergers or loops, by ignoring a Reply that repeats one already received for the same Transaction (for example a Query_Result with a Result Index already received).
    • C-5A Client shall check every retrieved Payload before using it: the Retrieve_Header's Record ID is the one requested, the Blocks add up to its Payload Size, and the Full Payload Checksum matches.
    • C-6A Client shall send a correct Device Identity, and should send a Client Device Name and its SysEx Device ID when it has them.
    • C-7A Client shall use timeouts so that a missing Server or a lost message never leaves it waiting indefinitely.
    • C-8A Client should ask its user to confirm before loading a retrieved Payload that would replace data on the device.
    • C-9A Client shall follow the flow control of Section 7.4: send each Store Block only when the Server asks for it, and acknowledge every Retrieve_Header and Retrieve Block it receives.
    • C-10A Client shall set Max Results no higher than the number of Query_Results it can receive back to back, and shall not rely on the Server pausing between them (Section 7.4).
    • C-11A Client shall not send Store Blocks larger than the Server's Max Store Block Size (Section 6.2).
    • C-12A Client shall ignore any bytes after the OnlineServer fields it knows, and shall ignore reserved Policy Flags (Section 4.2).
    • C-13A Client shall discover the Server it uses before its first Request after power-up (an Offer also gives the Server's MUID, so a Client may Retrieve an offered Record without discovering first), shall not choose automatically between Servers with the same name, and should rediscover a Server that stops answering (Section 7.1).
    • C-14A Client that implements Offers shall ignore an Offer that is not for it, shall answer one that is for it with Offer_Reply within the Client Offer reply time, and after Pending shall send a final Offer_Reply. After Accepted it shall Retrieve the Record from the Server that sent the Offer, and shall discard it unless the Retrieve_Header matches the Offer (Section 7.7).
    • C-15A Client shall not replace data stored in its memory with an offered Payload without its user's confirmation, unless its user has chosen to accept Offers automatically, and should answer Busy rather than interrupt an operation in progress.
    • C-16A Client that implements client discovery shall answer DiscoverClients sent to the broadcast MUID or to its own MUID with OnlineClient, sent to the Server's MUID with the same Transaction ID. It should announce itself with OnlineClient to the broadcast MUID, with Transaction ID 0, after power-up and whenever its MUID, SysEx Device ID or Device Name changes. It shall set the Accepts Offers flag only if it implements Offers.

    10Security Considerations

    MIDI 1.0 offers no confidentiality, integrity protection or authentication, and MBSP Version 1 does not add them. Implementers and users should be aware of the following:

    • No authentication. Any device on the network can send any Request. Owner checks (for Delete and Replace) rely on Device Identity and SysEx ID, which any device can claim. They prevent accidents, not deliberate misuse.
    • Access Key in clear text. The Access Key is visible to every device on the network and should be treated as a convenience, not a password.
    • Integrity of control messages. Payloads are protected end to end by a CRC-32, but other fields are protected only by the 7-bit Message Checksum. An error that changes two or more bytes of a message can occasionally pass that check, for example turning a Delete_Request into a Delete of a different Record ID. Such errors are rare on MIDI links, and Owner-only Delete limits the damage to the requesting device's own Records.
    • Advisory OnlineServer and OnlineClient. Policy Flags and limits are not authenticated, and any device can send OnlineServer under any Server Name. Likewise, any device can send OnlineClient claiming any Device Identity and Device Name. A Server's device list is therefore advisory, and is never used for ownership checks (S-23).
    • MUIDs are not authenticated. A device that sends messages using another device's MUID makes that device draw a new MUID (Section 5.5), which interrupts its open Transactions.
    • Untrusted Payloads. A retrieved Payload may have been stored by another device or altered on the Server. Clients must validate data before loading it, and should take particular care with anything that changes firmware or calibration. The CRC-32 detects accidental corruption only: anyone who alters a Payload can supply a matching checksum.
    • Offers. Any device can send an Offer using any Server's MUID. An Offer cannot change a device's data by itself: the Client decides whether to fetch the Record and asks its user before replacing stored data (C-15). The Retrieve it allows without the Access Key is limited to the offered Record, for the Client that accepted it, for the Offer Lifetime. A Client should treat an offered Payload as untrusted, like any other.
    • Firmware. Servers should refuse firmware by default (Section 8.4). A Client should never apply firmware retrieved over MBSP without the user's explicit confirmation.
    • Denial of service. A misbehaving device can flood the network or open many Transactions. Servers should limit concurrent Transactions and apply timeouts.
    • Privacy. Patch names, tags and set lists may reveal information about a user's work. Server operators should treat exported databases accordingly.

    Future versions may define authentication within an MBSP extension (Sub-ID #2 other than 00h).

    11.1Block Size and Pacing

    A MIDI 1.0 DIN connection carries 3,125 bytes per second. Each Data Block message adds 24 bytes of overhead when no Access Key is used: 20 for the envelope and 4 for Block Index and Block Size. Table 11 shows the resulting transfer times. Acks travel on the return connection, so they do not use the sending direction's bandwidth, but each Block waits for one round trip: a 22-byte ack takes about 7 ms on DIN, plus the receiver's own processing time. With 256-byte Blocks this adds roughly 8% to the times below.

    A Query_Result is typically 50 to 90 bytes long, and at most 251 bytes (32-character Device and Payload Names and eight 16-character tags). A full page of 127 typical results therefore takes about 2 to 4 seconds to arrive over DIN, but can arrive almost at once over USB. Clients with small receive buffers should keep Max Results small (Section 7.4).

    11.2Payload Encoding

    Payload bytes travel inside System Exclusive and are therefore 7-bit. MBSP does not define how a device encodes its data into a Payload: each manufacturer packs Payloads however it chooses, and the Server stores them as opaque bytes. Only the device that wrote a Payload, or another device that understands the same format, needs to decode it.

    In practice, most device data already exists as the 7-bit body of the device's own System Exclusive dumps and can be stored as it is. A device with 8-bit data may use any 7-bit encoding, for example the common scheme that packs 7 bytes into 8 with their high bits gathered in a leading byte. Manufacturers are encouraged to reuse the encoding of their existing System Exclusive dumps, so the same data can move between MBSP and their other tools unchanged.

    11.3Use over MIDI 2.0

    MBSP messages are MIDI 1.0 System Exclusive messages and can be carried unchanged over MIDI 2.0 Universal MIDI Packet transports in Data 64 (System Exclusive 7-bit) messages. No MIDI 2.0-specific behavior is defined in this version.

    The choice of UMP Group, and any routing between Groups, are matters for the transport, outside this specification. A Client and a Server can communicate only if they use the same Group or the transport routes between their Groups. As on MIDI 1.0 (Section 3.2), discovery reaches only the devices that the routing connects.

    11.4Relationship to MIDI-CI

    MBSP borrows the MUID concept from MIDI Capability Inquiry, including Source and Destination MUIDs in every message, but does not require MIDI-CI, so that it can be implemented on MIDI 1.0 devices that lack MIDI-CI support. MIDI-CI Property Exchange addresses a different need: a controller reading and setting properties of a device. MBSP lets a device save its own data to a third party. A future version could advertise MBSP support through MIDI-CI Profile or Property Exchange mechanisms.

    MBSP MUIDs follow MIDI-CI's format: the same 28-bit range, the same broadcast value 0FFFFFFFh and the same reserved range 0FFFFF00h-0FFFFFFEh. MBSP and MIDI-CI messages are distinct, so neither protocol sees the other's MUIDs. A device that implements both may use one MUID for both, provided it draws a new one for both when either protocol detects a collision. Such a device shall follow MIDI-CI's rules for generating that MUID, and therefore shall not keep it across power cycles as Section 5.5 otherwise allows a Server to do.

    12Open Issues for Review

    The proposer requests the reviewers' guidance on the following points.

    Issue 1Assignment of a Universal Non-Real Time Sub-ID #1 for MBSP. The draft uses 6Ah as a placeholder (Section 13).
    Issue 2Ownership of identical units. A Record's Owner is the Device Identity and SysEx Device ID, so identical units that send no SysEx Device ID share one Owner (Section 5.4). Should a future version add an optional persistent identifier for each unit, such as a Client Instance ID, which would also distinguish several independent Clients in one device?     Issue 4Access Key. The Access Key is sent in clear text and offers convenience rather than security (Section 10). Is it worth keeping in Version 1, or should access control be left to a future authenticated extension?

    Appendix BReference Implementations

    Three open implementations accompany this proposal. The first two were used to check every example and procedure in this document. All three are published in one repository, github.com/MidiHax/midi-bulk-storage-protocol, together with this document.

    • WebMIDI Server. A complete MBSP Server that runs in a web browser using the Web MIDI API, with records kept in the browser's database, import and export of the whole database, a record browser, a list of the Clients on the network (client discovery), Offers of Records to devices, and a built-in protocol self-test. It can be run without installing anything at midihax.github.io/midi-bulk-storage-protocol/sample-server/.
      Source: github.com/MidiHax/midi-bulk-storage-protocol/tree/main/sample-server
    • Studio Client. A test Client that emulates a studio of ten devices, including two units of the same model, and exercises every message, every Query filter, and the error cases (bad checksums, missing Blocks, Data Blocks for no open Store, lost final Status replies, replacement of stored Records, unknown Records, unknown Message Types, messages for other MUIDs, Server Names shared by two Servers, invalid fields and firmware refusal), verifying every reply byte for byte. Its devices also announce themselves, answer DiscoverClients and answer Offers in every way a Client can.
      Source: github.com/MidiHax/midi-bulk-storage-protocol/tree/main/sample-client
    • TouchOSC Snapshot Panel. A small demonstration Client built as a TouchOSC control surface, with faders, knobs, an XY pad, toggles and a mode selector. Its Save button stores a snapshot of the controls on an MBSP Server, and its Load button lists the panel's snapshots and restores the one the user taps. It discovers every Server on the network and lets the user choose between them, announces itself to Servers, and asks its user to accept or decline a snapshot a Server offers.
      Source: github.com/MidiHax/midi-bulk-storage-protocol/tree/main/touchosc-panel

    The Server and the Studio Client share one protocol codec. In testing over a MIDI loopback, the Client completed more than 450 randomized operations against the Server, with up to six devices active at once, without a protocol error. The TouchOSC panel was tested live with two Servers on the network, discovering both and saving to and restoring from the one selected. In automated tests it also ran against two Servers at once, storing on each separately.
